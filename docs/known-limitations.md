# 已知局限性与能力边界

本文列出这个系统**明确不做什么、做不到什么、以及尚未被验证的部分**。

写它的目的有三个：避免使用者和审阅者对系统产生超出实际的期待；给答辩或评审一个可直接引用的边界说明；让后续改动知道哪些约束是有意保留的，而不是待修的 bug。

本文与 `docs/project-fact-baseline.md` 分工不同：那份文档记录**已被复核的事实**，本文记录**已知的不足与边界**。两者冲突时，以那份为准。

---

## 一、不是医疗产品

系统的伤病识别与安全拦截是**运动训练层面的启发式判断**，不是诊断。

- 急症信号（胸闷、头晕、晕厥、呼吸困难等）触发的是「立即停止、尽快就医」话术，系统**不做任何医学判断**，也不推测病因。
- 伤病冲突检测依赖规则表（关键词 → 禁止动作对）与语义档案匹配，覆盖的是**常见组合**，不是临床知识体系。
- 判定为「安全」只意味着**未命中已知冲突模式**，不等于该训练对使用者安全。

任何界面与文档都不得出现「诊断」「治疗」「替代医生」这类表述。

## 二、与初始设想的差距：动作分析是文本的，不是视频的

这是最容易被误解的一点，单列出来。

项目设计文档 §9「不做（v1 范围外）」第一条即为「视频/图片动作姿态分析（需 CV 模型，v2 考虑）」。当前实现的「动作分析」是：

> 用户输入**动作名 + 训练感受的文字描述** → 检索该动作的标准要领与相关知识 → 由大模型给出问题、原因、建议与替代动作。

它**没有**摄像头采集、没有人体关键点提取、没有角度计算、没有动作计数。仓库内不存在任何 CV 相关代码或依赖。

因此以下说法都是错的：系统能"看"出用户动作标不标准；系统通过视频判断动作对错；系统基于姿态识别纠正动作。

要做成视频版需要引入姿态估计模型，并自建标注数据集才能给出可复核的准确率——那是另一条技术路线，不在当前范围内。

## 三、生成质量：外推是共性，不是个别现象

RAGAS 对 68 条查询的评测结果（`eval/ragas_results.json`）：

| 指标 | 数值 | 含义 |
|---|---|---|
| 上下文相关性 | 0.864 | 检索环节可靠 |
| 忠实度 | 0.436 | **生成时有相当比例的内容超出给定上下文** |
| 答案相关性 | 0.513 | 组织答案时与问题的贴合度中等 |

分题型看，忠实度普遍落在 0.42~0.45 之间，**与题型关系不大**——这正是系统要设置事实核查器与安全门的原因：既然生成侧无法完全杜绝外推，就不能直接信任模型输出。

需要说明的是，**评测集规模有限**（主集 206 条，RAGAS 子集 68 条），这些数字反映的是特定版本、特定模型下的表现，不是长期准确率承诺。

## 四、检索与知识的已知缺口

**知识块数量无法静态核验。** README 声明的知识块数保存在 PostgreSQL 的 `knowledge_chunks` 表里，静态清单无法确认。要复核必须先重跑摄入流程（`python -m src.rag.knowledge_ingestion`）。`verify_project_facts.py` 会就此持续输出警告，这是设计如此，不是缺陷。

**LLM 批量扩展的知识文档只校验结构。** `data/knowledge/` 中由脚本生成的文档，其校验函数 `validate_doc()` 只检查字数、标题、核心要点、列表这些**结构条件**，不校验内容安全性与事实准确性。安全关键内容不走这条生成路径。

**安全判定不依赖知识库。** 事实核查器的规则引擎与语义档案是独立的，删掉整个知识库它仍能拦截高危组合。好处是安全不被知识库质量拖累，代价是**补充知识文档不会自动提升安全性**——两者需要分别维护。

**动作库词表存在覆盖缺口。** 计划里出现动作库中不存在的动作名时，系统照常交付，且**不向用户展示**这一点。这是已知的取舍（词表覆盖不全），不是遗漏。

**动作图示覆盖 71%。** 338 个动作中 240 个有图，其余 29% 是外部数据集本身未收录的（瑜伽体式、普拉提、波比跳及部分中文习惯叫法）。缺图时界面不显示任何占位——有意如此，见 README。

## 五、运行与部署边界

**账号体系是本地账号，不是多租户服务。** 它解决的是「这台机器上谁是谁」：scrypt 加盐哈希 + HttpOnly Cookie 会话 + 按身份隔离业务数据。**没有**注册审核、邮件找回、审计日志、权限分级、并发配额。

**运行契约是 `localhost:8503`。** 这不是一个可以直接暴露到公网的服务。默认只监听本地，未配置任何令牌时 `/admin/*` 失败关闭。

**成本控制是单机级别的。** 当日 LLM 成本上限依赖 Redis 计数，Redis 故障时降级为放行。参考量级：单份训练计划约 ¥0.32（含数十次模型调用），单次问答约 ¥0.01。

## 六、不可由仓库独立复核的部分

按本项目的事实标准，以下内容**不作为可验证事实**，仅作背景说明：

- **开发时间线**：项目 2026-04 起在本地开发，2026-07-01 才初始化 Git 仓库，因此 `git log` 的最早提交晚于实际开工约三个月，且早期提交是批量落地的。这段属于开发者一手陈述，无法由仓库文件证实。
- **外部服务的历史状态**：历史评测输出记录了当时的运行结果，但那些外部服务、模型版本与数据版本当前未必可复现。历史评测产出被计为**工件**，不构成生产准确率。

| `verify_project_facts.py` 只采集不比对 | 事实基线需要人工复核，脚本本身不会因数字漂移而失败 | 有意设计，改动时需人工比对 |
