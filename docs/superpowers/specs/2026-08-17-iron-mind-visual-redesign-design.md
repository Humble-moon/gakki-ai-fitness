# IRON MIND 视觉与关键体验改造设计规格

日期：2026-08-17  
项目：`/Users/mt/Desktop/gakki-ai-fitness`  
范围：方案 A——视觉改造＋关键体验修复  
视觉方向：A「精炼工业运动」为主，融入 B「温暖专业教练」

## 1. 背景与目标

当前前端是一个约 2425 行的原生 HTML/CSS/JavaScript 单文件页面，已有明确的暗黑工业风，但存在信息密度、响应式、交互稳定性、可访问性和流式渲染边界问题。

本次改造的目标不是重写产品或更换框架，而是在保留现有 FastAPI + SSE 接口和原生前端技术路线的前提下：

1. 让页面更像成熟的运动科技产品，而不是技术 Demo；
2. 让用户更快理解“我可以做什么、下一步该做什么”；
3. 修复会直接中断核心任务的 DOM 生命周期和流式状态问题；
4. 让桌面、平板、手机都有合理的信息层级；
5. 提高键盘、屏幕阅读器和 reduced-motion 用户的可用性；
6. 建立安全、稳定、可维护的动态内容渲染边界。

### 自评：范围必要性

视觉单独调整无法解决“新对话后无法提问”“进度条被清空”“移动端任务被表单阻挡”等问题；这些问题直接影响用户对新视觉的感知，因此纳入关键体验是必要的。暂不纳入后端认证、任务队列、完整前端拆分和大规模测试重构，避免本次范围失控。

## 2. 已确认的设计决策

### 2.1 页面结构

桌面端保留“左侧训练档案＋右侧任务工作区”，但将左侧分为档案摘要和详细编辑区；右侧固定为 Tab、任务说明、状态区和结果区。

移动端默认展示任务 Tab 和训练档案摘要，详细档案通过可折叠面板打开。训练计划页可默认展开档案；动作分析和知识问答优先让用户直接开始任务。

页面状态显式分为：`empty`、`editing`、`loading`、`streaming`、`success`、`error`。状态切换只更新所属区域，不通过重建根节点破坏其他组件。

### 2.2 视觉系统

主色为深黑蓝背景、炭黑面板、橙色行动强调、柔和森林绿完成状态、暖白正文和灰蓝辅助文本。橙色只用于当前任务、主按钮和进度；绿色用于安全/完成；不以低对比度作为唯一层级手段。

正文建议 14–16px，辅助说明 12–14px，metadata 11–12px；中文使用系统/Noto Sans SC 字体栈，英文仅用于品牌和少量技术状态。

卡片使用 12–16px 轻圆角、单层边框、低强度渐变和克制 hover；保留“锻造进度线”作为主要品牌动效，减少漂浮火星、噪点和持续 glow，并加入 `prefers-reduced-motion`。

### 2.3 组件与交互

- 三个主功能使用语义化 Tab：`role=tablist`、`role=tab`、`role=tabpanel`，支持方向键和清晰焦点。
- 场景、示例问题、历史记录、上传和删除操作使用原生 button/label。
- 所有输入补充 `label for` 关联；动态阶段使用 `aria-live=polite`；错误使用 `role=alert`；请求中按钮设置 `aria-busy`。
- 训练计划结果区拆分为进度、教练建议、流式预览和最终结果。
- 动作分析区拆分为输入、结论、问题、建议、安全提醒和参考动作。
- 知识问答保持稳定的问答外壳；“新对话”只清空消息、重置会话和统计，不替换 `#qa-output` 的结构。
- 所有用户、LLM、知识库和动作库内容都视为不可信，优先使用 `textContent`/文本节点和安全 DOM 构造；避免动态数据直接拼接 HTML。

## 3. 数据流与状态设计

### 3.1 训练计划

现有 SSE 事件映射：

- `stage` → 更新稳定的阶段标题和进度；
- `advice_chunk` / `advice_done` → 更新教练建议区；
- `planner_done` / `retriever_done` → 更新阶段 metadata；
- `writer_chunk` / `writer_done_raw` → 更新流式预览；
- `factcheck_done` → 更新安全审查状态；
- `done` → 渲染最终计划并进入 `success`；
- `error` 或断流 → 进入 `error`，保留已有内容并提供重试。

禁止在 `stage` 事件处理中清空整个结果根节点。

### 3.2 动作分析

保留 `/api/analyze-exercise`，将 `stage`、`writer_chunk` 和 `done` 分别映射到阶段区、分析预览和结果卡片。重复请求应有明确的 loading/取消策略；结果中的动作名称、建议和引用均通过安全渲染。

### 3.3 知识问答

保留 `/api/ask-question`。消息容器和输入区域在整个会话期间稳定存在；新会话只重置会话 ID、消息、统计和引用。`think_chunk` 只显示为可收起的思考状态，`answer_chunk` 追加到当前回答文本节点，`done` 生成来源卡片和完成状态。

### 3.4 请求生命周期

本次至少为每类请求保留可追踪的 active request 状态，并为重复点击、切换 Tab、新会话和页面离开提供取消或防并发处理。错误需要区分网络错误、HTTP 验证错误、服务端错误和 SSE 中断。

### 自评：数据流决策

保留现有事件名称可以减少后端改动；按区域映射可以直接解决当前进度条和问答 shell 问题。统一 SSE client 是合理的长期方向，但如果本次直接拆分全部前端文件，风险和范围会显著增加，因此本次只抽取必要的共享逻辑，完整拆分留作后续专项。

## 4. 响应式规则

- 桌面（约 1100px 以上）：档案侧栏＋主工作区；问答来源可放在侧栏或回答下方。
- 平板（约 768–1099px）：档案摘要置于任务内容附近，重要统计和引用改为紧凑卡片，不直接隐藏。
- 手机（约 767px 以下）：任务 Tab 位于上方；档案默认收起；训练日按纵向卡片显示，动作信息改为“名称／训练参数／注意事项”三层；来源使用折叠卡片。
- 所有断点都保证主要按钮可见、正文可读、内容不依赖横向滚动。

## 5. 不在本次范围内

以下问题已识别，但单独排期：

1. 文件真实删除 API、保留策略和文档数据清理；
2. 统一 FastAPI Pydantic schema 与规范化 422；
3. 管理端点认证、生产 CORS 收紧；
4. 上传异步任务化、流式大小限制；
5. 完整拆分 `index.html` 为 styles/js 模块；
6. FastAPI 集成测试和完整浏览器回归测试；
7. 认证、用户身份和长期记忆隔离；
8. 数据库、Docker 和后台摄入任务专项。

这些项目不应在本次视觉改造过程中顺手扩大，以保持可验证性。

## 6. 验收标准

### 视觉

- 桌面首屏的任务标题、Tab、档案摘要、主操作和欢迎引导清晰可见；
- A 风格的深色运动科技感保留，同时具备 B 风格的可读性和温度；
- 重要正文不依赖低对比度和超小字号；
- 动画克制，`prefers-reduced-motion` 下不会持续播放大部分装饰动效。

### 功能

- 点击“新对话”后仍可正常发送下一条问题；
- 计划生成的阶段进度不会因首个 SSE 事件消失；
- 计划、动作分析、问答的 loading/success/error 状态可辨识；
- 切换 Tab 不会破坏其他功能的稳定 DOM；
- 手机宽度下可完成三类核心任务，计划动作信息不被挤压。

### 可访问性与安全

- 键盘可以访问并操作 Tab、场景、示例问题、上传和主要按钮；
- 动态阶段和错误有合理的辅助技术播报；
- 输入有程序化标签关联；
- LLM/知识库/用户输入中的 HTML 特殊字符不会破坏页面结构或被当作 HTML 执行。

### 自评与取舍

验收标准同时覆盖视觉、关键功能和可访问性，是因为本次目标是“视觉＋关键体验”，只截图好看而核心流程中断不能视为完成。暂不把后端依赖服务可用性纳入前端验收；在没有 API Key、Docker 数据服务时，可先验证页面、状态切换和 mock/错误路径。
