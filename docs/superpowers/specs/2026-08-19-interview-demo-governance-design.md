# 面试展示版项目治理与优化设计

日期：2026-08-19
项目：gakki-ai-fitness
目标：将项目整理为事实可信、指标可解释、链路可演示、失败可复现、边界清晰的 localhost 单用户 AI 应用展示版。

## 1. 范围与非目标

### 目标

本轮聚焦四个阶段：

1. 统一项目事实与版本口径；
2. 重构评测说明和验证入口；
3. 提升本地 Demo 的可复现性与核心链路验证能力；
4. 在证据稳定后引入条件化检索，并通过对比实验验证收益。

### 非目标

本轮不实施：

- 登录注册和完整多用户权限体系；
- 生产级人工审核后台和 reviewer 闭环；
- Kafka、微服务拆分或 LangGraph 迁移；
- 医疗级认证、医疗诊断能力或合规认证；
- 公网生产部署和生产 SLA 承诺；
- 无人机真实控制。

项目继续明确定位为 localhost 单用户演示。

## 2. 当前事实基线

代码核对确认的核心链路为：

```text
FastAPI
  → Planner
  → Retriever
  → Writer
  → FactChecker
  → SSE terminal event / safe persistence
```

已实现或可从代码确认的能力包括：

- 三条主要业务 SSE 接口：训练计划、动作分析、知识问答；
- 上传文档和管理/摄入接口；
- 自研 Python Orchestrator，而非 LangGraph；
- Planner 的 LLM JSON 路由、Skill 校验和关键词安全覆盖；
- AgenticRAG、关键词/向量检索和 MCP 补充检索；
- Neo4j Cypher GraphRAG 实现；
- Writer 结构化生成和重写；
- FactChecker 与规则型 HITL 升级判定；
- Semantic Cache 的精确/语义两级查询；
- Redis 短期会话和长期画像 KV；
- Provider fallback、degraded 语义、空流处理和 CircuitBreaker；
- SSE `done/error/cancelled` 终止协议；
- 前端隐藏内部 Writer JSON，并将结果结构化渲染。

当前可直接核对的数据规模：

- `seed_exercises.json`：338 个动作；
- `data/knowledge/`：162 个 Markdown 文档；
- README 声称 824 chunks，但未发现独立、当前版本的可复核统计结果，因此暂不作为强事实；
- 主 Golden Dataset：206 条；
- 知识评测子集：54 条；
- 条件上下文生成评测：10 条；
- RAGAS 结果：68 条子集。

## 3. 阶段设计

### 阶段一：事实与版本口径治理

新增单一事实基线文档，至少包含：

- 当前代码/数据版本标识；
- 统计日期；
- 数据规模和统计命令；
- API、SSE 事件和 MCP Tools/Resources；
- 模型、Embedding 和端口；
- 测试命令及 marker 选择范围；
- 评测数据集分层；
- 已实现、测试验证、历史结果、设计方案四类状态；
- 每个数字的证据路径和推荐对外话术。

历史报告不删除，统一标注 historical/deprecated/not-comparable/design-only，避免改写历史证据。

### 阶段二：评测体系和验证入口

在不伪造新结果的前提下，重整评测说明：

- 检索评测：206 主集与 54 知识子集分开；
- 生成评测：明确为条件上下文生成质量，不称为完整 E2E；
- 安全评测：单独描述样本、风险类别、FNR/FPR 定义；
- 业务链路 E2E：单独验证 HTTP → Agent → SSE terminal；
- 负载评测：标明本地单机、短样本和非生产 SLA。

评测报告必须记录：数据集、样本数、代码版本、模型版本、Prompt 版本、参数、日期、指标公式和已知限制。对指标增加范围校验；若采用多标签特殊定义，使用准确名称并解释公式，不能让普通 Recall 出现大于 1 的表述。

新增或整理统一验证入口：

```text
make test
make e2e
make eval
```

其中默认测试和 integration/live 测试的范围必须清楚标识。

### 阶段三：Demo 可复现化

提供清晰的运行模式，优先保证面试展示：

- demo：最小依赖或 fake provider，快速启动；
- full：连接 PostgreSQL、Redis、Neo4j、MinIO 和真实 Provider；
- test：运行默认离线测试；
- e2e：运行核心链路验证。

README 补充：

- 环境准备；
- 一条命令启动；
- 数据初始化；
- 三条业务链路操作步骤；
- 成功、失败、重试和取消的可观察结果；
- 端口与依赖；
- localhost 单用户边界；
- 不支持医疗诊断和生产部署的限制。

在不改变现有安全语义的前提下，优先增加离线 fake/demo 路径和真实依赖检查，减少演示对外部服务的脆弱依赖。必要时补充浏览器级回归，但不把静态前端契约测试冒充真实 UI E2E。

### 阶段四：条件化检索

在阶段一至三完成并有基线后，按查询类型选择最小必要路径：

```text
精确动作名       → 动作库直接查询
普通知识问题     → 向量检索
关键词明显       → 向量 + 关键词
多跳关系问题     → GraphRAG
召回不足         → Query Rewrite
高风险问题       → FactChecker 强化路径
必要时           → Re-rank
```

每次变更记录：

- Recall/Precision/NDCG/MRR；
- 端到端延迟和各阶段耗时；
- Token 与调用次数；
- 错误率、空结果率和安全结果；
- 触发比例；
- 数据集和代码版本。

只有在同一数据集、同一指标定义和可比运行条件下，才允许宣称优化收益。向量检索、关键词检索和 GraphRAG 在互不依赖时可以并行化，但必须有独立超时、取消传播和并发上限；不在本轮默认重写整个 Orchestrator。

## 4. 验收标准

1. README 能指导面试官从零启动 Demo；
2. 三条业务链路各有成功、失败和恢复验证；
3. 对外数字都有证据路径和统计日期；
4. 历史指标、当前指标和设计指标不再混用；
5. 评测报告明确数据集、模型、版本、公式和限制；
6. 默认测试、核心 E2E 和评测命令有明确范围；
7. 前端不展示内部 JSON；
8. 项目明确标记为 localhost 单用户演示；
9. 不使用未经证实的医疗级安全、整体零漏报、生产 SLA 等表述；
10. 条件化检索有可复现的前后对比，没有只增加组件而无收益证据。

## 5. 风险与取舍

- 不立即迁移 LangGraph：当前主要问题是证据治理和验证，不是编排框架能力；
- 不立即引入 Kafka：当前为单进程线性 Pipeline，缺少实际异步规模需求；
- 不继续无条件扩展 GraphRAG/MCP/Agent：先证明查询类型和收益；
- 不删除旧评测：保留历史可追溯性，但显式标记不可比；
- 不把人工升级判定称为人工审核闭环；
- 对 `review_pending` 仅创建单机内存审核 artifact，并通过 SSE `done` 返回审核摘要；不提供真实审核人、账户、approve/reject API 或持久化审核队列。前端只展示审核编号、风险原因、禁止项和下一步，且不把待审核结果渲染、保存或迭代为训练计划。
- 不把 localhost 演示能力包装成生产系统。

## 6. 推荐实施顺序

1. 生成事实基线和评测索引；
2. 修正 README、评测说明和面试事实引用；
3. 整理 Makefile/脚本验证入口；
4. 增加 Demo 启动与核心 E2E 验证；
5. 复核现有真实运行结果；
6. 设计并实现条件化检索；
7. 重新运行可比评测并记录结果；
8. 最后同步面试资料和简历话术。

本设计不承诺阶段四一定提升所有指标；如果实验显示复杂路径没有收益，应保留更简单路径并在报告中记录该结论。
